# Main Controller unpair workflow (Phase 1)

This phase adds the durable backend workflow and Flutter status reconciliation.
It does not add ESP32 firmware, broker ACLs, or a way to provision Firebase
device credentials.

## State and reservation

Operations live in `controllerUnpairOperations/{operationId}` with
`operationId`, `houseId`, `controllerId`, `requestedBy`, `createdAt`,
`updatedAt`, `expiresAt`, `status`, `deliveryAttempts`, and `nextDeliveryAt`.
The operation ID is generated by the Functions runtime with 24 cryptographic
random bytes encoded as base64url.

The state path is:

```text
pending -> prepared -> completed
    |                     
    +-> failed (only if no prepared acknowledgement before expiresAt)
```

While pending/prepared, `houses/{houseId}.mainControllerId` and
`controllers/{controllerId}.activeHouseId` remain assigned. The documents also
carry a server-written `pendingUnpairOperationId`; the controller status is
`unpair_pending` or `unpair_prepared`. An operation in `pending` expires after
24 hours. Expiration marks the operation failed and removes only its pending
markers; it does not release either relationship. Prepared operations remain
retryable until completion.

Only the authenticated device completion callable atomically clears both
registry links. `pairedAt`, `lastSeenAt`, and the controller document remain.
`lastUnpairOperationId` on the House supports UI recovery after a lost callable
response. Re-pairing clears that pointer.

## Callable contracts

- `requestMainControllerUnpair` (owner-authenticated):
  request `{houseId, controllerId}`; returns `{operationId, houseId,
  controllerId, status, expiresAt, createdAt, updatedAt, deliveryAttempts}`.
  Repeated requests while the operation is active return the same operation.
  The legacy callable name `unpairMainController` is retained as an async
  alias; it no longer clears the registry directly.
- `getMainControllerUnpairOperation` (approved owner who requested it):
  request `{operationId}`; returns the operation status fields above.
- `retryMainControllerUnpair` (approved owner who requested it): request
  `{operationId}`; queues an immediate best-effort delivery and returns current
  status. A scheduled retry also runs every minute.
- `acknowledgeMainControllerUnpairPrepared` and
  `acknowledgeMainControllerUnpairCompleted` (device-authenticated): request
  `{operationId, controllerId}`. The completion transaction clears House and
  Controller links; duplicate matching acknowledgements return the existing
  state.

The device acknowledgement callables require a Firebase ID token bound to the
deterministic controller Firebase Auth UID, with Admin-issued custom claims
`deviceType: "main-controller"`, matching `controllerId`, and the current
credential generation. The registry must mark the credential active (or the
operation must be an already-completed retry). Functions check revocation time,
operation/controller/House assignment, and revoke/disable the identity after
completion. No arbitrary unauthenticated acknowledgement endpoint is
provided. See [device identity provisioning](MAIN_CONTROLLER_DEVICE_IDENTITY_PHASE2.md)
for the custom-token exchange and legacy-controller migration contract.

## MQTT delivery

Functions publishes only from the trusted server runtime, over MQTT TLS with
Functions secrets `MAIN_CONTROLLER_MQTT_HOST`,
`MAIN_CONTROLLER_MQTT_PORT`, `MAIN_CONTROLLER_MQTT_USERNAME`, and
`MAIN_CONTROLLER_MQTT_PASSWORD`, plus the broker CA PEM in
`MAIN_CONTROLLER_MQTT_CA_CERT`. It uses QoS 1 and a dedicated topic:

```text
smartassist/{houseId}/controllers/{controllerId}/control
```

The payload is `{v:1,type:"unpair",phase:"prepare"|"commit",operationId,
houseId,controllerId,expiresAt}`. A pending operation sends `prepare`; a
prepared operation sends `commit`. Retries use the same operation ID so the
future firmware must make both phases idempotent. Existing
`smartassist/{houseId}/{ROOM1_NODE|ROOM2_NODE}/cmd` and `events` topics are
unchanged.

QoS 1 proves broker receipt, not device receipt. The broker ACLs and firmware
credentials are absent from this repository and are not verified. Provision
the Functions publisher credentials with publish access to the controller
control path, and configure device-side subscribe ACLs scoped to the correct
controller/House. The shared MQTT username/password must not be treated as
proof of device identity; acknowledgements are separately authenticated with
the device Firebase token and custom claims.

## Deployment prerequisites and limitations

Before deploying, set the five Functions secrets above and deploy the Firestore
index definitions in `firestore.indexes.json` together with the updated rules.
No deployment was performed as part of this change. The scheduler requires the
Firebase/Google Cloud Scheduler integration for scheduled Functions.

Without firmware, per-device Firebase credential provisioning, and broker
ACLs, the operation can be created and retained but cannot be securely
completed by a real controller. Pending operations remain visible and retry;
timeouts do not clear registry assignments.
