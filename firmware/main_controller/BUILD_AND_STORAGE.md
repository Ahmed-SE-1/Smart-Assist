# Main Controller ESP32 development build

Target: ESP32-WROOM-32 (classic ESP32), 4 MB flash. Firmware is built as an
ESP-IDF project with Arduino-ESP32 as a component.

## Pinned software

- ESP-IDF: `v5.1.4`
- Arduino-ESP32 component: `3.0.7` (based on ESP-IDF 5.1.4)
- ArduinoJson: `7.2.1`
- PubSubClient: Git tag `v2.8` (CMake FetchContent)
- Partition table and NVS encryption settings: checked in under `idf_project/`

ESP-IDF's Component Manager resolves the registry manifest and creates
`idf_project/dependencies.lock` during the first `idf.py reconfigure`. The lock
file must be generated by the solver, not edited by hand. Commit it after first
dependency resolution; subsequent builds use it. PubSubClient is pinned to its
`v2.8` release tag in the top-level CMake file.

## Windows PowerShell setup and build

If Git or Python 3.11 is missing, install them and open a fresh PowerShell:

```powershell
winget install --exact --id Git.Git
winget install --exact --id Python.Python.3.11
```

Then install ESP-IDF v5.1.4 and its ESP32 compiler/tools (CMake and Ninja are
installed by ESP-IDF's installer):

```powershell
git clone --recursive --branch v5.1.4 https://github.com/espressif/esp-idf.git "$env:USERPROFILE\esp\esp-idf-v5.1.4"
Set-Location "$env:USERPROFILE\esp\esp-idf-v5.1.4"
.\install.bat esp32
. .\export.ps1
Set-Location "D:\Ahmed\SmartAssist-FYP\SmartAssist App\Smart-Assist\firmware\main_controller\idf_project"
.\build.ps1
```

For another checkout location, change only the final `Set-Location`. The script
checks ESP-IDF 5.1.4, sets the `esp32` target for a fresh project, resolves
pinned dependencies and builds. Keep `sdkconfig` and `dependencies.lock` for
repeat builds. Build never erases or flashes a device.

To flash and monitor after reviewing the first-time storage note below:

```powershell
idf.py -p COM5 flash monitor
```

Replace `COM5` with the board's serial port. This writes the bootloader,
partition table, and application to their configured addresses. It is not an
erase-all operation, but it changes flash contents and the partition table.

## Partition layout

The table assumes a 4 MB module and ends exactly at `0x400000`:

| Name | Type | Offset | Size | Purpose |
|---|---|---:|---:|---|
| `nvs` | data/nvs | `0x9000` | `0x6000` | Encrypted Preferences namespace |
| `nvs_keys` | data/nvs_keys | `0xF000` | `0x1000` | NVS XTS key material |
| gap | — | `0x10000` | `0x10000` | Alignment/reserved |
| `factory` | app/factory | `0x20000` | `0x3E0000` | Application |

The bootloader occupies the ESP-IDF default area below the partition table at
`0x8000`. There are no overlapping partitions. This is a single factory app;
there is no OTA slot in this physical-test layout.

## Secure storage behavior and development limits

`app_main` checks the selected target's `nvs` and `nvs_keys` partitions, checks
the key partition's encrypted flag, reads or generates NVS keys only when the
key partition reports uninitialized, then calls `nvs_flash_secure_init` before
Arduino/Wi-Fi startup. Corrupt or incompatible NVS is not erased or repaired.
The firmware sets its protected-storage flag only after successful secure
initialization and a successful Preferences read/write probe. A failed check
halts startup; pairing and credential writes cannot fall back to plaintext.

This config enables ESP-IDF NVS XTS encryption but deliberately does not enable
Flash Encryption or burn eFuses. Therefore the generated NVS keys in
`nvs_keys` are not protected from someone who can read the flash chip. The
encrypted NVS API is exercised, but this is development-grade at-rest
obfuscation and is not resistance to physical flash extraction. No production
security mode or irreversible eFuse operation is part of this setup.

The device-generated pairing recovery secret is stored only during its
10-minute recovery window. It is distinct from the owner pairing token and is
bound server-side to controller ID, House ID, and credential generation. The
owner pairing token stays in RAM only. Firebase custom tokens and ID tokens are
RAM-only; the Firebase refresh token, controller identity, House assignment,
credential generation, and unpair recovery fields use the encrypted
Preferences namespace.

## First-time flash and serial checks

Do not run `idf.py erase-flash` as part of the normal setup. A blank device's
blank `nvs_keys` partition receives generated keys on first boot. Existing
devices may have plaintext or differently laid out NVS at the new offsets; the
firmware intentionally will not migrate or erase it. If initialization fails
on a device whose old NVS contents may be discarded, back up anything needed
and manually erase only the `nvs` and `nvs_keys` partitions using ESP-IDF's
`parttool.py` and the generated `build/partition_table/partition-table.bin`.
After building but before first flash, these explicit destructive commands
erase only those partitions:

```powershell
$parttool = Join-Path $env:IDF_PATH 'components\partition_table\parttool.py'
python $parttool --port COM5 --partition-table-file .\build\partition_table\partition-table.bin --partition-table-offset 0x8000 erase_partition --partition-type data --partition-subtype nvs
python $parttool --port COM5 --partition-table-file .\build\partition_table\partition-table.bin --partition-table-offset 0x8000 erase_partition --partition-type data --partition-subtype nvs_keys
```

Run them only when intentionally wiping saved state. This deletes saved Wi-Fi
and controller state; losing `nvs_keys` makes previously encrypted NVS
unreadable. No erase command is included or run by the build scripts.

On Serial Monitor at 115200 baud, check for:

- `Encrypted NVS initialized; key partition and secure NVS API verified`
- `Pairing disabled: encrypted NVS read/write probe failed.` must not appear.
- After pairing, normal Wi-Fi, Firebase authentication, MQTT TLS and BLE logs.
- On unpair, the existing prepare/commit and reboot recovery acknowledgements.

The success log verifies software initialization on the actual device; it does
not prove that flash encryption/eFuse protection is enabled. Physical tests
must still verify BLE behavior, Firebase token exchange and refresh, MQTT TLS,
ESP-NOW channel 0 and the configured Node MACs, PIR forwarding/retries, relay
mapping, power interruption during credential writes, and unpair recovery.
